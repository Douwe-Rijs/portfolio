## Overview

Allseas crews keep operational logbooks in **Bull** — welding records, NDT
inspections, engine-room events, warnings. Meanwhile the vessels' sensor
data lives in Grafana dashboards. The two records describe the same reality
and were never shown together: to explain a spike in a graph, you opened a
second application and matched timestamps by hand.

This plugin closes that gap. It is a Grafana **datasource plugin with a Go
backend** that queries the Bull API and renders logbook entries as
**annotations** — vertical markers drawn directly onto any time-series
panel, each carrying the crew's own words.

## The problem

A first version of the plugin existed but had a blocking flaw: **on board a
vessel, no logbooks appeared at all** — precisely where the data mattered
most. Beyond that bug, everyone querying through a single shared account
meant every Grafana user saw every logbook, regardless of what their Bull
role allowed. And shore-side users had no way to use the plugin against the
central Bull instance at all.

## How it works

The Go backend authenticates to the Bull API with NTLM (credentials in
Grafana's encrypted secure storage — never in the browser) and exposes
logbooks, categories and entries to the query editor. A data-repository
layer caches logbook and category lists, deduplicates concurrent requests
with `singleflight`, and refreshes user-role data every ten minutes.

Two features I built define the plugin's current shape:

**Per-user access control.** Each query carries the authenticated Grafana
user. The backend maps that user to a Bull login and checks the requested
logbook against their cached Bull roles — server-side, per request. A mate
sees the deck log; they do not see logbooks their role excludes. Mapping
identities across the two systems was its own bug hunt: display names were
ambiguous, so the plugin now derives the login from the user's e-mail
address.

**Dual deployment.** The same plugin now talks to a vessel's local Bull
instance or the central shore instance — a config toggle, two credential
sets, one codebase. This is what made the plugin usable both on board and
in the office.

## Fitting Grafana's grain

Rather than inventing custom panels, the plugin leans on Grafana's native
machinery so logbooks behave like any other data:

- **Annotations** render entries as time-anchored markers on existing
  panels — no dashboard redesign needed.
- **Template variables** let dashboard authors define regex-filtered
  logbook or category variables, so one dashboard serves a whole fleet.
- **Cascading category selection** mirrors Bull's category-chain hierarchy
  in a single compact control.

## Results

The plugin is released (v1.1.0) with vessel and central connectivity, and
documented with a user manual on the internal docs site. Crews and
office engineers see logbook entries in context on the graphs they already
use: a red marker at the moment of a warning, the crew's exact words one
hover away. The vessel bug that blocked on-board use is fixed, and logbook
visibility now follows each user's actual Bull permissions.

Honest limits: annotation density can get visually heavy on long time
ranges (Grafana draws every marker), and the role cache means a permission
change can take up to ten minutes to propagate.

## Lessons learned

- **Meet users inside their existing tool.** The entire value is that
  nobody has to open a second application — the logbook comes to the graph.
- **Shared service accounts are a liability.** Real per-user authorization
  required backend enforcement and an identity-mapping strategy, not UI
  filtering.
- **Native extension points age best.** Annotations and template variables
  survive Grafana upgrades; bespoke UI would not have.

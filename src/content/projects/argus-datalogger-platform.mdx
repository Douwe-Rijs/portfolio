## Overview

Every Allseas vessel streams sensor data into InfluxDB: thruster power,
winch temperatures, positions, flows — tens of thousands of series per ship.
InfluxDB is superb at storing that data and terrible at explaining it. What
_is_ `AU-433X0.winch,winch=S4`? What unit? Which physical device? Which other
vessels have the same sensor?

**Argus** answers those questions. It is a metadata platform — a Go REST API
over PostgreSQL, a Grafana app plugin, and an exporter that discovers what
exists in InfluxDB — that gives engineers and data scientists one structured,
searchable front door to every signal in the fleet. I built features across
all three components, from error-handling middleware to the guided tour.

## The problem

The raw time-series database has no opinion about structure. Measurement and
tag names encode meaning by convention only, units live in people's heads,
and a decade of legacy "parameter IDs" from the previous datalogger
generation still circulate in reports and scripts. Finding the right series
meant asking the person who set up the logger — a process that does not scale
across a fleet.

The goal: a **single metadata model** describing what every series _is_ —
its device, class, unit and data type — kept automatically in sync with what
actually exists in InfluxDB, and browsable by anyone with Grafana access.

## The data model: two parallel trees

The core design organises everything into a schema tree (what kinds of data
exist) and an instance tree (the concrete devices and their values). A
_signal class_ like "gearbox temperature, float, °C" is defined once; each
winch on each vessel then has a concrete _signal_ instance of it. That
one-to-many structure is what lets a data scientist ask "give me this
temperature on every vessel" without knowing any vessel's tag conventions.

## An API that cannot drift from its spec

The backend is OpenAPI-first: the spec and the SQL schema are the sources of
truth, and `oapi-codegen` + `sqlc` generate the server interfaces and
type-safe query code from them. Handlers contain only business logic. I
leaned into that discipline for every feature I added:

- **RFC 9457 error responses.** A composable error-handler chain converts
  every failure — schema-validation errors included — into a structured
  problem object with a unique `ARGUS-…` code. The full stack trace is
  logged server-side under the same code, so a user screenshot is enough to
  find the exact failure in the logs.
- **Observability.** A `/metrics` endpoint (OpenTelemetry → Prometheus)
  plus HTTP request logging that includes the Grafana username, feeding an
  operations dashboard of status-code counts.
- **Transactions.** A generic `QueryTransactionManager` gives every handler
  the same begin/commit/rollback discipline, with read-only transactions at
  repeatable-read isolation for queries.

## From query strings to ASTs

Grafana needs to turn a signal class into a real InfluxQL query. The first
version built query strings by hand — fragile, and reviewers agreed it was
the wrong interface. I rewrote it on the official `influxql` AST library:
the endpoint now parses and returns the **abstract syntax tree** of the
query, which the Grafana datasource converts into its native query parts.
Grafana injects its own time filter at runtime; nothing is string-spliced.

The same thinking produced the **legacy-ID endpoint**: give it a vessel and
an old datalogger parameter ID, get back the site and signal UUID. Years of
existing references keep working against the new platform.

## Making it usable, not just correct

The first UI mirrored the database — hierarchies, "Channel Classes",
auto-import flags. Real users found it opaque. I reworked it based on that
feedback: flat lists instead of nested trees, plain names, jargon hidden or
renamed, and an **interactive guided tour** through the app. Filters sort
lexicographically; every table row opens an inspector with the signal's
attributes and a **live time-series preview** — the fastest possible answer
to "is this the series I want?"

## Results

Argus is in **beta on the fleet Grafana stack**, versioned at `/api/v3beta`
with CI/CD pipelines I built deploying the API, exporter and app via Helm.
A single vessel's catalogue already unifies over 21,000 signals, each
discoverable by name, class or device and previewable in one click — a task
that previously required knowing InfluxDB tag conventions by heart.

Honest limits: it is still a beta. The UI-simplification work is ongoing —
some renamings ("Signal Group", "Asset") are being rolled out iteratively,
and the signal-activeness indicator users liked is not yet reliable enough
to ship.

## Lessons learned

- **Generate the boring parts.** With the HTTP and SQL layers generated
  from specs, code review focused on logic, and the API could grow to 36
  endpoints without becoming inconsistent.
- **Error handling is a user feature.** Structured problem objects with
  correlatable codes turned "it's broken" support messages into one-line log
  lookups.
- **Ship vocabulary, not schema.** The data model's precision is essential
  internally — and exactly what to hide from users. Plain words and flat
  lists beat correctness in the interface.
